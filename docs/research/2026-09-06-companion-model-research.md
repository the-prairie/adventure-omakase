# Model selection for Ask Omakase

Research date: September 6, 2026. Scope: documentation and existing evidence only; no paid inference, application change, deployment, or comparative benchmark was run.

## Recommendation

Use **Claude Sonnet 5 as the quality-first evaluation baseline**, but withdraw any implication that it is already the best model for this app. Compare it with **Gemini 3.8 Flash at low thinking** and **Kimi K2.6** on identical evidence. Gemini is the strongest documented value challenger for this shortlist; Kimi deserves a direct trial because it meets the broad tool-use requirements and is the user's proposed alternative. This is an engineering recommendation from documented capabilities and integration fit, not a measured quality ranking.

If only one adapter can be built first, Sonnet is defensible for a small friends release where per-request cost is modest. If minimizing recurring cost is the priority, start the comparison with Gemini. OpenAI GPT-5.6 Luna is a compelling additional budget candidate; include it before selecting a high-volume default. A chat or coding subscription is not the application API billing mechanism.

The major finding is that **retrieval and validation matter at least as much as model choice**. The current tools search curated discoveries and English Wikipedia leads. They do not provide broad Japanese local-business search, route computation, or reservation availability. A better model cannot establish facts absent from the supplied evidence. Keep the application's validators and explicit invitation confirmation regardless of provider.

## What the app actually asks a model to do

The [engine](../../apps/friends/src/ask-engine.ts), [contracts](../../apps/friends/src/ask-contract.ts), and [ADR 0007](../decisions/0007-ask-omakase.md) define a bounded read-only loop: choose two or three regional options, check source pages, copy exact quotations, propose separately timed activity/lunch parts, and return nested JSON. The app checks source IDs, quotation substrings, selected region and times, and retains publishing authority. Limits include four model calls, four source reads, one repair, and 75 seconds. This is not unrestricted travel-agent browsing.

Japanese acceptance cases need Japanese venue pages and quotations, name/romanization matching, local date interpretation, closure exceptions, and geographically sensible meal transfers. None of the sources below establishes a comparative winner on those exact requirements. Chinese-language or general multilingual capability is not evidence of Japanese travel superiority.

## Integration traps that affect the decision

**Sonnet:** adaptive thinking is enabled by default; `max_tokens` covers thinking plus response, and non-default sampling parameters are rejected. Its newer tokenizer produces approximately 30% more tokens than Sonnet 4.6 for equivalent text, so equal-token estimates are only illustrative. The adapter must support the provider's schema subset: remove unsupported array bounds from the provider schema while retaining our own validator. Native Claude citations conflict with structured outputs; our existing `sourceId` and exact-quote JSON approach can remain. First-use schema compilation adds latency. Sources: [migration](https://platform.claude.com/docs/en/docs/about-claude/models/whats-new-sonnet-5), [structured output limitations](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), [citation incompatibility](https://platform.claude.com/docs/en/build-with-claude/citations).

**Gemini:** start with `low`, not `minimal` (unsupported on 3.8). Remove deprecated sampling parameters. Preserve provider reasoning state correctly: the Interactions API has thought steps and signatures; manually managed generateContent histories must return thought signatures in their original parts. Function responses must retain call identity. The existing OpenAI-style history cannot simply be forwarded unchanged. Sources: [3.8 migration](https://ai.google.dev/gemini-api/docs/latest-model?hl=en), [Interactions thinking](https://ai.google.dev/gemini-api/docs/thought-signatures), [generateContent signature rules](https://ai.google.dev/gemini-api/docs/generate-content/thought-signatures).

**Kimi:** thinking defaults on, sampling values are fixed by thinking mode, and the current tool loop must preserve `reasoning_content`; tool choice in thinking mode permits only auto/none. Our first model turn currently forces `check_sources`, so that turn requires disabling Kimi thinking or changing the orchestration deliberately; it is not a transparent endpoint swap. Its quickstart supports disabling thinking, also worth testing for the 75-second deadline. Official benchmark guidance recommends streaming to avoid idle-connection interruptions; that is not a measured latency promise. API docs expose JSON-object mode rather than a verified strict-schema guarantee. Sources: [quickstart](https://platform.kimi.ai/docs/guide/kimi-k2-6-quickstart), [benchmark guidance](https://platform.kimi.ai/docs/guide/benchmark-best-practice), [chat API](https://platform.kimi.ai/docs/api/chat).

**All providers:** retain semantic validation, rejection/repair handling, request cancellation and measured usage. Replace Cloudflare-specific neuron reservations with provider-aware token/dollar budgets when adding an external API. Select reasoning effort explicitly, count every loop turn and repair, and do not compare only final visible answer tokens.

## Search and Maps are separate product decisions

Google's Search/Maps access is relevant to local discovery, but switching to Gemini while retaining the current tools does not enable it. Its current [pricing page](https://ai.google.dev/gemini-api/docs/pricing) lists separate grounding charges; older sections use different free allowances and charging units. Budget against the selected model/tool endpoint and confirm its actual usage accounting before enabling.

The [Gemini terms](https://ai.google.dev/gemini-api/terms) place specific display, modification and retention restrictions on Maps-grounded results. Our shared reusable place research and editable invitations need a distinct integration design rather than treating Maps output as interchangeable scraped page evidence. This concern applies to built-in Maps grounding, not ordinary Gemini calls over our own evidence. Google's free and paid tiers also differ in whether content is used to improve products; see the [pricing page](https://ai.google.dev/gemini-api/docs/pricing).

Kimi's [pricing documentation](https://platform.kimi.ai/docs/pricing/chat-k26.md) currently warns that web search is being updated and is not recommended in the near term. Its [quickstart](https://platform.kimi.ai/docs/guide/kimi-k2-6-quickstart) separately identifies thinking-mode incompatibility with the built-in search tool. Keep our controlled tools in a Kimi trial.

## Cost at the observed workload

The prior preflight recorded 6,715 input and 2,185 output tokens across two calls, three source reads, 21.478 seconds, and 362.635086 neurons (usage-equivalent $0.003989). See [current status](../audits/CURRENT_STATUS.md). One successful response is not a reliability or latency distribution. It included GRAVITATE as a Namba-area alternative, illustrating that technically valid cards can still be geographically poor.

## Evidence limits and next evaluation

No trustworthy public comparison found here proves a winner on this app's Japanese source-grounded invitation task. The [Berkeley function-calling leaderboard](https://gorilla.cs.berkeley.edu/leaderboard.html) observed during research was last updated April 12, 2026, preceding several candidates. Coding and broad agent scores are not interchangeable with venue-hours reasoning, exact quotations or geographic fit. [TravelBench](https://arxiv.org/abs/2512.22673v3) offers a useful method—single-turn, multi-turn, unsolvable requests and cached tools—but does not settle the current shortlist.

Proposed bounded evaluation, not run: 12 synthetic scenarios × three repetitions × three candidates = 108 complete task runs (up to 432 model calls under the current four-call limit). First hold source snapshots and tool responses constant; then run three live journeys per finalist to assess retrieval separately. Include activity plus lunch, Japanese-only hours, closed venues, unavailable sources, distant same-region venues, conflicting commitments, ambiguous requests, impossible windows, prompt injection in pages, changed snapshots and interrupted requests. Include a dietary requirement and an explicit no-availability case; never score assigning the Tokyo friend as successful group planning.

Score hard authority/privacy violations separately from quality. Compare first-pass valid cards, exact and semantically supporting quotations, realistic geography/transfers, appropriate uncertainty, latency including repairs, deadline completion, and total cost including failed attempts. Inspect cold-schema and warm runs. Proposed screening bar: zero authority/privacy violations, zero fabricated citations displayed, no known closed/out-of-window option accepted, and at least 34 of 36 tasks yielding usable results per candidate within the deadline. These are design targets, not observed results or a statistical reliability guarantee. Inspect and fix every hard failure before live release. Choose the least costly model that meets the acceptance bar; the current documentation justifies a shortlist, not a production winner.
